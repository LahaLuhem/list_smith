# How list_smith works

The parts, and what each seam between them promises. The reasons are in
[`APPENDIX.md`](../APPENDIX.md). Change a seam, change its row.

## The parts

| Part                                                                               | Its job                                                                                              |
|------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|
| [`ListSmith`](../lib/src/widgets/list_smith.dart)                                  | the public widget, picks the sync or async engine                                                    |
| [async engine](../lib/src/widgets/async_list_view.dart)                            | owns the paging state and every fetch, runs the reloads, and feed and search as 2 views on one state |
| [paging state](../lib/src/data/pagination/models/paging_state.dart)                | the loaded pages and where the stream stands. Its `status` names the surface to show                 |
| [`PagedView`](../lib/src/widgets/paged_view.dart)                                  | picks the surface for the status, the app's builder or a neutral default                             |
| [`KeyedListView`](../lib/src/widgets/keyed_list_view.dart)                         | both engines' scroll view: keyed rows and headers, or a surface instead, and the near-end trigger    |
| [`ScrollAnchor`](../lib/src/widgets/scroll_anchor.dart)                            | holds the row the user is reading still as rows above it change, or the pull's room does             |
| [`RefreshBinding`](../lib/src/widgets/refresh_binding.dart)                        | wires `custom_refresh_indicator` and places the indicator                                            |
| [reloads](../lib/src/data/refresh/models/reload.dart)                              | the `Reload` strategies, each run through the `ReloadContext` the engine hands it                    |
| [`ListSmithController`](../lib/src/data/control/models/list_smith_controller.dart) | code's verbs, forwarded to the engine                                                                |
| [sync engine](../lib/src/widgets/sync_list_view.dart)                              | an in-memory list with search, no fetching                                                           |

## Known gaps

Both need an odd sequence, under an `EditTransition`:

- a create whose save fails after a re-read already shows the server's copy shrinks away, then pops
  back
- a delete whose save fails mid-exit brings its row back even if the row was removed again during
  that exit, until the next re-read
